ARCHITECTURE SUMMARY (must be understood before reading sub-tasks)
================================================================================

  - AUTH IS MANDATORY: unlike cce-insights-ui, there is NO VITE_AUTH_ENABLED
    bypass flag. initAuth() always runs before render; an unauthenticated user
    is always redirected to Keycloak login.
  - STATIC SIDEBAR: the sidebar (Users, Roles, Menus) is NOT driven by
    GET /me/menus — that endpoint exists for OTHER consoles (cce-insights-ui)
    to consume, not this one. Authorization here shows up as inline 403s on
    the screen that made the call, never as a hidden nav item.
  - NO OPTIMISTIC UI ANYWHERE: every mutation waits for the server; buttons
    show a pending state; queries invalidate on success. There is no
    onMutate cache-patching pattern in this app.
  - FULL-REPLACEMENT PAYLOADS: the Menus tab, Permissions tab and the user
    Roles editor all send the COMPLETE desired set on save, never a partial
    diff — but Save is disabled until the set actually differs from the
    last-fetched state.
  - TWO INDEPENDENT TABS on Role Detail (Menus, Permissions) — two separate
    save actions, two separate query keys, never combined into one "Save"
    button.
  - KEYCLOAK_SYNC_FAILED gets ONE shared component, reused on the user-create
    form and the Permissions tab — never a generic error toast.
  - CONTRACT-FIRST: build against MSW mirroring
    ../cce-admin-service/docs/api-reference.md until the real backend's
    corresponding sub-task (see cce-admin-service-subtasks.txt) is merged,
    then swap the proxy target — no code changes needed if the MSW handlers
    were accurate.

SUB-TASK U2: Auth Module
================================================================================

DESCRIPTION:
  F-01. keycloak-js Authorization Code + PKCE (S256), mandatory — no bypass
  flag. Must exist before any API call can be made, since every call needs a
  live token.

DELIVERABLES:
  1. auth/keycloak.ts — keycloak-js instance, client id `cce-admin-ui`,
     `initAuth()` using `onLoad: 'login-required'`, `pkceMethod: 'S256'`
  2. auth/context.tsx — exposes `getToken()`, current Keycloak profile
  3. main.tsx: `initAuth().then(render)` — app does NOT render until login
     resolves (no flash of unauthenticated content, no race where a page
     mounts before a token exists)
  4. A background interval calling `keycloak.updateToken(70)` every 60s
  5. Env vars: VITE_KEYCLOAK_URL, VITE_KEYCLOAK_REALM, VITE_KEYCLOAK_CLIENT_ID
     (developer-setup.md §2)

ACCEPTANCE CRITERIA:
  - Visiting any route with no session redirects to Keycloak login
  - After login, the app renders and `getToken()` returns a valid JWT
  - Token silently refreshes before the 60s mark without forcing a re-login
  - No `VITE_AUTH_ENABLED`-style bypass exists anywhere in the code

SUB-TASK U10: User Create & Edit
================================================================================

DESCRIPTION:
  F-11. The most state-heavy screen: one create flow (single POST) and one
  edit flow (four independent actions on the same page).

DELIVERABLES:
  1. pages/UserFormPage.tsx (mode="create" | "edit") + hooks/useCreateUser,
     useUpdateUser, useUpdateUserStatus, useUpdateUserRoles, useResetPassword
  2. Create: RHF + Zod form, single POST /users submit, pending state on the
     one button, no separate "sync"/"send invite" step shown to the user —
     the backend triggers the invite email automatically as part of the
     same call
  3. Edit: four SEPARATE actions/buttons (profile PUT, roles PUT, status
     PATCH, password reset POST), each with its own pending state and error
     surface — do not collapse into one "Save" that fires all four silently
  4. 502 KEYCLOAK_SYNC_FAILED on create uses U5's shared `SyncFailedNotice`
     and does NOT clear the form's entered values
  5. 409 EMAIL_IN_USE renders inline on the email field
  6. `201` with a `warnings` array (invite email failed to send, user still
     created successfully) — navigate to the user as normal, show the
     warning text inline as a dismissible banner, NOT a blocking error and
     NOT the same treatment as a 502

ACCEPTANCE CRITERIA:
  - PRD milestone F4 exit check (create/edit half): create and edit flows
    both working against MSW, including the 502 state via U4's toggle
  - A failed create (502) leaves every field exactly as the admin entered it
  - A `201` response carrying a `warnings` entry still navigates to the
    created user and shows the warning inline, distinct from both the 502
    path and a clean 201 with no warnings
